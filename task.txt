Проект «Умный бэкенд»
Описание проекта
Вам предстоит реализовать бэкенд-приложение, работающее с базой данных. У приложения будет API, состоящее из нескольких тестовых методов.
Основная идея проекта
Идея заключается в следующем:
Вы подготовите API и таблицы БД для работы «конструктора API и таблиц БД».
Подготовите API-клиент для локальной нейросети.
После запуска бэкенда сможете через «конструктор» запрашивать у нейросети всё необходимое для построения API, таблиц БД и проверочных данных для задач заказчика.
Вы будете сохранять наработки нейросети в БД.
Будете пробовать исполнить её инструкции: распарсить JSON, выполнить SQL, запустить HTTP-эндпоинты и выполнить запросы к ним.
Вы попросите нейросеть исправить инструкцию, если что-то пойдёт не так, и затем попробуете снова.
В этом проекте вы совместите два подхода: классическое программирование веб-приложений и работу с ИИ в режиме REPL (request, evaluate, print-loop — запрос, выполнение, вывод результата в цикле). Сохраняя всё, что придумала нейросеть, вы формируете так называемый контекст — данные, по которым нейросеть сможет вспомнить, что она делала ранее.
Этапы выполнения задания
В этом задании вам понадобится предварительная подготовка окружения. С помощью Docker и Compose подготовьте чистую базу данных и запустите локальную нейросеть — бесплатный LLM-движок Ollama.
Затем реализуйте привычный проект на Spring Boot + JPA, подключите его к БД и нейросети, реализуйте API по работе с конструктором и таблицы для хранения данных о наработках нейросети. На этом этапе вы можете использовать нейросеть в режиме обычного ассистента в чате.
После добавьте тесты для «конструктора» и убедитесь, что служебные функции работают как надо.
Далее вам надо приступить к работе над основной частью приложения — запросам к ИИ, разбору ответов и исполнению инструкций от ИИ в БД и API. Здесь вам помогут технологии JDBC, Markdown, JSON и REST Template. Подробнее о них мы расскажем ниже.
Основной фишкой этого этапа будет «непрерывность» разработки, тестирования и использования умного бэкенда.
Нейросети бывают неточными, это нормально. Вам надо будет научиться с этим работать: правильно интерпретировать ответы ИИ, их качество и целостность и активно давать нейросети обратную связь.

Детали кода проекта
Инфраструктура
Перед началом работы опишите и запустите инфраструктуру проекта. Она состоит из двух контейнеров.
Второй контейнер — приложение по запуску ИИ-моделей Ollama. В нём используется производительный движок llama.cpp. В сочетании с готовыми к использованию на обычных компьютерах репозиториями Ollama стал настоящим двигателем в развитии «домашних» нейросетей. Всё взаимодействие с программой происходит через консольный клиент, по идеологии напоминающий Docker CLI.
Например, просмотреть список доступных сетей поможет команда ollama ls, а скачать выбранную нейросеть можно запустив команду ollama pull net:tag. В этом проекте вы запускаете Ollama в Docker, поэтому консоль будет доступна внутри контейнера.
services:
  ollama:
    ...
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu, compute]
Для контейнера Ollama подключите внешнее хранилище volume для внутренней папки /root/.ollama. Это поможет сохранить скачанные модели на будущее, так как они не меняются.
Для обоих контейнеров используйте compose-файл. После запуска контейнеров выполните команду docker ps. Вы увидите два недавно запущенных контейнера.
Перейдите в командную строку контейнера Ollama и выполните команду ollama help для вывода списка команд. Скачайте модель для разработки, ознакомившись со списком моделей по ссылке. Например, можно скачать модель gemma3:4b.
Бэкенд-конструктор
Приложение на Spring Boot потребует стартеры для web-запросов API, подключения к БД через JPA и модули для работы с репозиториями Spring Data. Не забудьте задать в application.properties параметры подключения к БД и настройки по созданию структуры БД из заранее заготовленного SQL-файла в resources.
Базовый API конструктора должен содержать несколько методов по созданию нового модуля приложения. Модулем назовём те наборы API, таблицы БД и тестовые данные, которые вам поможет создать ИИ. Само описание модуля требуется хранить в БД, в таблицах конструктора. Управлять конструктором рекомендуем через Postman (или аналог) с помощью заготовленных запросов.
Для создания полноценого и более удобного интерфейса чата вам может пригодиться HTML-страница, которую сгенерирует нейросеть по описанию API конструктора.
Модель работы конструктора можно описать так. Вы начинаете обсуждение фичи модуля с нейросетью через API конструктора, весь диалог фиксируется в базе данных.
Если в процессе обсуждения ИИ возвращает корректные JSON-данные, подходящие для фичи, вы фиксируете фичу и её параметры в БД отдельным запросом к API конструктора. По сути его функция будет заключаться в обработке последнего ответа нейросети.
Если эта фича описывает API, то оно должно автоматически заработать (обрабатывать запросы с выводом в лог).
Если это фича настройки БД, она должна быть выполнена один раз. Например, создание таблицы или внесение данных.
Если это фича по работе с БД, она должна быть сохранена в базу и связана с соответствующим API в рамках модуля.
Всё это возможно, если вы будете следить за текстовыми идентификаторами полей, которые придумает нейросеть. В рамках этого проекта это могут быть простые GET/POST-запросы с последующими SELECT/INSERT/UPDATE запросами к БД. Последовательность создания фич может быть любая, учитывайте это.
При этом сами фичи внутри модуля могут объединяться в последовательности обработки данных. Поэтому важно предусмотреть возможность сохранения многих фич разных типов, привязанных к одному модулю.
Мы предполагаем, что вы примените свои навыки по декомпозиции задачи и сформируете свой вариант наборов сущностей и API. Важно, чтобы они в полной мере позволяли решить задачу конструктора.
Использование ИИ
Современные ИИ-модели могут довольно легко решить задачи построения стандартного API на Spring Boot. Но это решение будет представлено вам в виде обычного исходника. Такой способ работы с ИИ не слишком подходит для динамического создания модулей в ходе работы приложения. В этом задании вам не подойдёт вариант свободного ИИ-бота, генерирующего исходный код.
Вам придётся использовать гибридный подход. Со стороны бэкенда вы обозначите ряд формально описанных возможностей конструктора и будете передавать это описание нейросети, а она будет стараться в указанных правилах реализовать фичи по пользовательской задаче, реализуемой в рамках одного модуля.
Эти фичи будут содержать описания и правила, накладывающие ограничения на структуру данных на разных этапах. Также они могут содержать текст запросов или обращения к другим сервисам, а также обработку запросов от клиентов и сервисов. Рассмотрим возможные варианты фичей.
Динамический API. Эта задача довольно легко раскладывается на описание собственно API — REST, это довольно ограниченный набор из HTTP-методов, параметров запроса и JSON-содержимого запроса и ответа. Сложите всё это вместе в динамический эндпоинт (об этом ниже) — и получите контроллер под задачу пользователя.
Динамические HTTP-запросы. Можно также описать запрос к стороннему сервису с помощью RestTemplate. Нейросеть подскажет набор параметров для запроса и схему обработки ответов.
Динамические SQL-запросы. Достаточно описать таблицу БД: название и набор полей с типами, а также наборы SQL-запросов с именованными параметрами, которые можно взять из получившегося выше контроллера. Данные для ответа пользователю можно взять из результатов выполнения того или иного SQL. Например, сгенерировать тестовые данные по известной схеме таблицы БД. Также на БД можно возложить ряд пользовательских функций, таких как поиск, подсчёт, аналитические расчёты. Для этого нейросеть может подготовить SQL-запросы, которые просто вернут нужный результат.
Произвольные вычисления. Сложнее дело обстоит с произвольной логикой сервисов — это действительно сложная, неформализуемая часть любого веб-приложения, в которой воплощена бизнес-логика проекта. Мы упоминаем её лишь для полноты — в рамках проектного задания вам достаточно ограничиться только формализованными частями конструктора умного бэкенда.
Если вас интересует тема создания неформального пользовательского сервиса, вы можете обратиться к теме интерпретируемых языков в JVM — например, запуск Groovy-скриптов из строковой переменной или специализированный язык Spring EL внутри экосистемы Spring Boot, который позволит вам выполнять достаточно сложные операции над имеющимися данными. А нейросеть вам в этом поможет.
Запросы к ИИ
Для выполнения запросов к ИИ существует простой API, совместимый с Ollama и другими чат-ботами. Выглядит он так:
Запрос:
POST /api/chat
{
  "model": "gemma3:4b",
  "messages": [
    { "role": "user", "content": "Hello!" }
  ],
  "stream": false
}

Ответ сервиса:
{
  "model":"gemma3:4b",
  "created_at":"2026-02-22T22:31:12.7130031Z",
  "message":{"role":"assistant","content":"Hello there! 😊 How can I help you today? Do you want to chat, need som
e information, or perhaps play a game? \n\nJust let me know what you have in mind!"},
  "done":true
Для API приложения Ollama существует maven-зависимость с готовыми сервисами для вызова и управления моделями, но мы рекомендуем также попробовать работать с сервисом через RestTemplate, так как это позволит использовать сам сервис Ollama в виде фичи для динамических запросов из будущего пользовательского API.
Одна из полезных возможностей при работе с моделями в Ollama — принудительное форматирование ответов в JSON. Это серьёзно упростит работу с нейросетью, так как бэкенд сможет разбирать ответы ИИ по известной схеме данных.
Например:
Запрос:
POST /api/chat
{
  "model": "gemma3:4b",
  "messages": [
    {"role": "system", "content": "Answer with json scheme {\"description\"\, \"type\", \"data\"}. Be precise"},
    { "role": "user", "content": "Create a SQL table 'test' with 'id' and 'value'" }
  ],
  "stream": false,
  "json": true
}

Ответ нейросети:
{
    "model": "gemma3:4b",
    "created_at": "2026-02-22T22:45:34.83431Z",
    "message": {
        "role": "assistant",
        "content": "```json\n{\n  \"description\": \"Creates a SQL table named 'test' with columns 'id' (INT) and 'value' (VARCHAR).\",\n  \"type\": \"SQL\",\n  \"data\": \"CREATE TABLE test (id INT, value VARCHAR(255));\"\n}\n```"
    }
}
Мы попросили выдать ответ в формате {description, data} — и получили его. Конечно, здесь нужно учитывать вероятностную природу нейросетей: иногда вы будете получать ответ в виде JSON, но внутри документа Markdown, иногда это будет вовсе не JSON или JSON, не соответствующий схеме. Поэтому вам необходимо реализовать гибкую функцию разбора ответа — используйте простой парсер Markdown для Java в виде maven-зависимости flexmark-java. Для JSON используйте ObjectMapper, обложите всё это в try..catch и не стесняйтесь возвращать содержимое exception.getMessage() обратно в чат с нейросетью, чтобы она внесла исправление с учётом всего контекста сообщений.
Если после нескольких попыток ничего не получается, возможно, стоит переформулировать запрос или системную инструкцию. Если размер переписки превысил рекомендуемый размер контекста для конкретной нейросети, стоит попробовать заново.
Подробнее о понятиях «системная инструкция», «запрос» и «контекст» нейросети вы можете почитать здесь.

Далее мы продемонстрируем простую цепочку запросов для задачи «Создание таблицы и наполнение тестовыми данными». В рамках шаблона тестового проекта опишем следующие эндпоинты.
/api/users
Для использования динамических API мы применяем специальный класс Spring для настройки маппинга и обобщённый контроллер, который будет разбираться с любыми API, которые мы создадим. Ниже мы покажем, как применить класс RequestMappingHandlerMapping для настройки конкретного эндпоинта. Дальнейшее использование совместно с ИИ остаётся за вами.
@Autowired
private RequestMappingHandlerMapping handlerMapping; //используем специальный бин

RequestMappingInfo mappingInfo = RequestMappingInfo //подготавливаем описание http-ендпоинта
        .paths("/api/users")
        .methods(RequestMethod.GET)
        .produces("application/json")
    .build();

//в отдельном классе описываем обработчик запроса
public static class EndpointHandlerForList {
        public static Method handlerMethod; //здесь мы получаем от Java ссылку на метод описанный ниже
        static {
            try {
                handlerMethod = EndpointHandlerForList.class.getMethod("handleRequest", HttpServletRequest.class, HttpServletResponse.class);
            } catch (NoSuchMethodException e) {
                throw new RuntimeException(e);
            }
        }

        public ResponseEntity<List<Map<String, Object>>> handleRequest(HttpServletRequest request, HttpServletResponse response) {
            return ResponseEntity.ok(new ArrayList<>());
        }

    }

//собираем всё вместе и регистрируем обработчик

handlerMapping.registerMapping(
    mappingInfo,
        new EndpointHandlerForList(//какие-то данные для связи запроса и описания запроса),
        EndpointHandlerForList.handlerMethod //ссылка на метод
);

Также вам может пригодиться пример использования RestTemplate для выполнения произвольных запросов к любым сервисам, которые подскажет ИИ. В таких случаях вам потребуется метод exchange и базовые сущности HttpEntity? для хранения любых возможных параметров.
HttpHeaders headers = new HttpHeaders();
headers.add("Authorization", "Bearer " + token);
HttpEntity<String> entity = new HttpEntity<>(headers);
var url = "http://localhost:8080/api/payments";
var method = HttpMethod.GET;
var res = new RestTemplate().exchange(url, method, entity, String.class);
return res.getStatusCode().toString();

Наличие работающего compose-файла.
Наличие pom.xml, успешная сборка проекта через Maven.
Наличие файла конфигурации application.properties.

Использование конкретных мапперов, @GetMapping, @PostMapping вместо @RequestMapping.
Разделение приложения на сервисы, контроллеры и дао (репозитории) на уровне пакетов.
Отсутствие логики в контроллерах.
